# 検証結果: SQS × Lambda 1000 多重（個体付番 PoC）

Kiro Roasters の梱包バッチ処理（DynamoDB Streams → SQS → 付番ワーカー最大 1,000 多重）の
実機検証ログ。sandbox 実機でしか出ない挙動と、受け入れ基準 R1〜R5・過渡特性 T1〜T2 の実測を記録する。

> このドキュメントは**随時追記**する。新しいシナリオ（方式比較 L_cmp、L3/L4、D 変更など）を
> 回したら、末尾の「追記テンプレート」に沿って節を足すこと。

- 仕様: `.kiro/specs/sqs-labeling-poc/`（requirements / design）、出典 `spec/aws-sqs-lambda-1000/`
- 観測ツール: `docs/poc/observe/`（`observe.sh` / `load.sh` / `to_csv.py`）

---

## 0. サマリ（全体結論）

全 10 試行（§4）を通して確定したこと:

1. **SQS を挟めば後続処理の同時実行を Streams のシャード数から切り離し、1,000 多重に到達できる**
   （第 3 回の Streams 直読み 640 止まりへの回答）。worker `MaximumConcurrency=1000` に張り付き、取りこぼし 0。
2. **1000 到達の律速は Lambda スケール上限ではなく「供給」。** Pipes 版 857→1000 の差も、中継 Lambda 版
   502→800→1000 の差も、投入の厚さ・継続時間で決まった。
3. **方式比較（T3）**: 既定（P=1）では Pipes が速く中継 Lambda は 502 止まり。だが中継 Lambda の遅さは
   **S×P（= オープンシャード数 4 × ParallelizationFactor）に律速された供給レート**が原因で、方式の限界ではない。
   - 供給総量を増やせば中継 Lambda でも 1000 到達（502→800→1000）。
   - `ParallelizationFactor` を P=10（S×P=40）にすれば、同じ 20 バッチで Pipes に並ぶ（502→1000、業務時間も 9 秒で同等）。
   - **S×P は供給の「レート」を縛るが、worker の「到達多重」は供給の「総量 × 継続時間」で決まる**（SQS がバッファで両者をデカップリング）。
4. **同じ下流なら処理時間は劣化しない**（worker Duration avg ~3,050〜3,160ms で一貫）。取りこぼしは全試行 0。
5. **worker Throttle は worker 自身の MaxConc=1000（= アカウント枠と同値）の天井が原因**（入口方式・食い合いではない。§4.9/§4.10）。
   食い合いは router と worker の同時ピーク時にのみ起こり得る潜在リスク。
6. **オンデマンドの書き込みスロットル（T2）は全試行 0**。瞬間 ~420 WCU/秒を吸い切った。ただし本日の高負荷で
   学習済みのため、「初動スロットル」を見るにはテーブルのリセットが要る（未実施）。
7. **投入方法のトレードオフ**: 一気に投入（STAGGER=0）は全体を速く終わらせるが、SQS 滞留が膨らみ 1 バッチの
   業務応答は遅くなる（1 バッチ中央値 9 秒 → 63 秒）。分散投入は 1 バッチの体感を速くする。
8. **運用の差**: Pipes はマネージドで速い・設定最小だが入口が CloudWatch で観測しにくい（`AWS/Pipes` 未発行）・
   Lambda 枠を使わない。中継 Lambda は IteratorAge/同時実行を観測でき P で調整できるが S×P を意識した設計と Lambda 枠が要る。

> 本検証では書き込みが一度もボトルネックにならなかった（WriteThrottle 0）ため、上記の結論は
> DynamoDB テーブルの書き込み学習状態に依存しない。

## 2. 実機デプロイで判明した不具合（合成テストをすり抜けたもの）

ローカルの vitest（型・CDK 合成アサーション）は通っていたが、`ampx sandbox` で実デプロイ・実行して
初めて顕在化した不具合。いずれも「実機でしか出ない」種類で、修正と回帰テストを入れた。

| # | 症状 | 根本原因 | 修正コミット |
|---|------|---------|------------|
| 1 | デプロイが `UPDATE_ROLLBACK_FAILED` で失敗 | EventBridge Pipes の source `batchSize=100` が、target=SQS の上限 10 を超過（SQS SendMessageBatch は 1 回 10 件まで） | `2bc284c` |
| 2 | 画面のタブが切り替わらない（全パネル表示） | `.panel{display:block}`（詳細度 0,1,0）が UA の `[hidden]{display:none}`（0,0,0）を上書き | `2217e85` |
| 3 | 画面 C/D で `batch not found`（`BATCH#BATCH%23...`） | API Gateway がパスパラメータを**デコードせず**渡し、`ensureBatchId` が `BATCH#` を二重付与 | `e57bb42` |
| 4 | seeder が 1 件も投入せずクラッシュ | seeder/worker が GSI 名まで要求する `resolveTableConfig()` を呼ぶが、construct は GSI 名の env を注入していない（最小権限） | `a63e3d5` |
| 5 | 投入後も全 unit が PENDING のまま（worker が全件失敗・無限リトライ） | Pipes の `inputTemplate` が Streams の `.N` を**文字列**で送り、worker の `typeof unit_count !== "number"` 判定で弾かれる。しかも catch が沈黙してログゼロ | `ce90ed5` |

教訓: CDK 合成テストは「env キー定数の一致」までは見ていたが、「各関数の env セットがハンドラの
実行時要求を満たすか」「API Gateway のデコード挙動」「Pipes の型射影」は検証範囲外だった。
いずれも実デプロイで初めて出る。

## 3. 受け入れ基準の実機確認（R1〜R5）

機能パイプライン（R1〜R4）は少量（unit_count=20）で一周を確認し、R5 は 1000 多重検証で確認した。

| ID | 要件 | 結果 | 根拠 |
|----|------|------|------|
| R1 | 滞留生成（PENDING 一括 INSERT・Streams NEW_IMAGE） | ✅ | seeder が 20/1200 件を PENDING で投入、Streams へ |
| R2 | 中継（INSERT のみ 1 レコード=1 メッセージ） | ✅ | Pipes 経由で SQS に全件到達、二重付番なし |
| R3 | 冪等付番（`attribute_not_exists(best_before)`、成功時のみ `labeled_count ADD`） | ✅ | 二重配信は条件で弾かれ、Duration ~390ms の短時間終了として観測 |
| R4 | 完了検知（`labeled_count==unit_count` で LABELED、キュー深度非依存） | ✅ | roast-batch が LABELED・`labeling_finished_at` 設定、SQS 深度に依存せず |
| R5 | 最大 1000 多重到達・張り付き | ✅ | **ConcurrentExecutions=1000 到達、約 3 分張り付き、Throttle 0**（§4.2） |

## 4. 1000 多重の実測（R5 / T1 / T2）

### 4.1 試行 1 — 供給律速で 857 止まり（供給不足の実証）

- 投入: `BATCHES=10 UNIT_COUNT=1200 STAGGER_SEC=20`（12,000 個体）
- `PROCESSING_TIME_MS=3000`

| 経過 | ConcurrentExecutions | queue_visible（滞留） | queue_inflight |
|------|----------------------|----------------------|----------------|
| +0s | 302 | 1,159 | 15 |
| +60s | 543 | 560 | 291 |
| +120s | 798 | 827 | 337 |
| +180s | **857（ピーク）** | **16（枯渇）** | 145 |

ピーク **857 多重**。+180s で滞留が 827 → 16 に急落＝**キューが枯れた瞬間に頭打ち**。
到達の律速は Lambda スケール上限ではなく「滞留量（供給）」だと確定。

補助指標（observe.sh 拡張版）:
- worker Duration avg ~3,080ms / p99 ~3,600ms、Errors 0、Throttles 0。
- **SQS 最古メッセージ滞留（最大）26 秒** ← 多重が足りずキューが一時的に詰まった（下の 1000 の回と対照）。
- **SQS 送信 12,000 / 削除 12,000（取りこぼしなし）** ← 投入した全個体が付番・削除された。

### 4.2 試行 2 — 供給を厚くして 1000 到達・張り付き

- 投入: `BATCHES=20 UNIT_COUNT=1200 STAGGER_SEC=10`（24,000 個体。試行 1 の 2 倍・間隔半分）
- `PROCESSING_TIME_MS=3000`

**立ち上がりカーブ（T1、observe.sh サマリ。窓起点 = 投入時刻）**

| しきい値 | 到達 |
|---------|------|
| 100〜750 多重 | +0 秒（最初のデータ点で既に 750 まで駆け上がり） |
| 900 多重 | +60 秒 |
| **1000 多重** | **+60 秒** |

**張り付きと下流（CSV、1 分粒度）**

| 時刻(JST) | ConcurrentExecutions | queue_visible | queue_inflight | worker Invocations/分 |
|-----------|----------------------|---------------|----------------|----------------------|
| 10:19 | 896 | 0 | 0 | 6,579 |
| 10:20 | **1,000** | 0 | 0 | 6,000 |
| 10:21 | **1,000** | 2 | 48 | 6,040 |
| 10:22 | 1,000 | 0 | 393 | 2,360 |

- **1,000 多重に約 3 分張り付き**（`MaximumConcurrency=1000` の天井が効いている＝それ以上増えない）。
- worker Throttles **0**、worker Errors **0**。unit テーブル WriteThrottleEvents **0**。
- 10:21 以降 `queue_inflight` が増加＝1000 で頭打ちになり処理が追いつかず「処理中」が溜まり始めた兆候。

補助指標（observe.sh 拡張版）:
- worker Duration avg ~3,140ms / p99 ~3,614ms（857 の回とほぼ同じ＝1000 でも処理時間劣化なし）。
- **SQS 最古メッセージ滞留（最大）3 秒** ← 多重が十分でキューが詰まらず常に新鮮（857 の回の 26 秒と対照的）。
- **SQS 送信 24,000 / 削除 24,000（取りこぼしなし）** ← 20 バッチ全個体を欠落なく付番。

**857 の回との対比（滞留の古さ）が示すこと**: 同じ worker・同じ D でも、多重が足りないと最古メッセージが
26 秒まで古くなる（処理が到着に追いつかない）が、1000 まで出ると 3 秒に収まる。SQS を挟むことで
「多重を増やして滞留の古さを抑える」制御が効いていることの実測。

### 4.3 Duration（1 件の処理時間。両試行で比較）

worker Duration（ms、`get-metric-statistics`、1 分粒度）:

| | avg | p99 | max |
|---|-----|-----|-----|
| 試行 1（857、4 点平均） | ~3,068 | ~3,587 | ~3,836 |
| 試行 2（1000、5 点平均） | ~3,055 | ~3,417 | ~3,737 |

- avg は両試行とも `PROCESSING_TIME_MS=3000` + 実処理 ~20〜140ms でほぼ一定。
- **同時実行が 857 → 1000 に増えても 1 件の処理時間は劣化しない**（SQS→Lambda は処理を遅くせず
  インスタンスを増やして捌く）。max の上振れ（~3,700〜3,800ms）はコールドスタート（Init）分。

### 4.4 T2（オンデマンドのスロットル追従）

- unit テーブル `WriteThrottleEvents` = **0**（両試行）。
- `ConsumedWriteCapacityUnits`（試行 2、Sum/分）: 6,621 → 12,579 → 12,000 → 13,240 → 3,560。
- 1000 並列の書き込みスパイク（ピーク ~13,000 WCU/分 ≈ ~220 WCU/秒）を**オンデマンドがスロットルなしで吸い切った**。
  「オンデマンド＝初動でスロットルが出る」という想定は、本検証の規模（unit 1 件 ~1KB、ピーク ~220 WCU/秒）では
  再現しなかった。これ自体が観測結果（より大きな項目サイズ・レートなら出る可能性は残る）。

## 5. 現時点の結論

- **SQS を挟めば、後続処理の同時実行を Streams のシャード数から切り離して 1,000 多重に到達できる**
  （第 3 回の Streams 直読み 640 止まりに対する回答）。Pipes 版の実測で `MaximumConcurrency=1000` に張り付き、
  Throttle 0。
- **1000 到達の律速は Lambda スケール上限ではなく「滞留量（供給）」。** 試行 1（857）→ 試行 2（1000）の
  差は入口でも worker でもなく、投入を厚くしてキューを枯らさなかったこと。
- **入口（Streams→SQS の中継）の速さが worker の到達多重に直結する（T3）。** 同条件 20 バッチで
  Pipes 版 1,000 vs 中継 Lambda P=1 版 502。中継 Lambda は Streams 読み出しが S×P の壁に律速され
  供給が遅い（§4.5）。ただし供給総量を増やせば worker は伸び（502→800→1000、§4.6）、
  **`ParallelizationFactor` を P=10（S×P=40）にすれば同じ 20 バッチで 1,000 到達し Pipes に並ぶ（§4.7）。**
  S×P は供給の「レート」を縛るが、worker の「到達多重」は供給の総量で決まり、P で供給レートを調整できる。
  取りこぼしはどの方式・設定でも 0。
- **同時実行が増えても 1 件の処理時間は劣化しない。** 両方式とも Duration avg ~3,080ms で一定。
- **オンデマンドは本規模のスパイクをスロットルなしで吸った**（T2 は本検証では未発生）。
- 立ち上がりは厚い供給下（Pipes）で **60 秒で 900→1000**（T1）。

## 4.5 試行 3 — 方式比較（L_cmp）: 中継 Lambda 版を同条件で測る

試行 2（Pipes 版・1000 到達）と**完全に同じ投入**（`BATCHES=20 UNIT_COUNT=1200 STAGGER_SEC=10` =
24,000 個体、`PROCESSING_TIME_MS=3000`）で、入口だけ `RELAY_MODE=lambda`（中継 Lambda `labeling-router`）
に差し替えた。下流（SQS・worker）は共通なので、差が出るなら「Streams → SQS の入口」の違いだけ。

**推移（60s 粒度）**

| 時刻(JST) | ConcurrentExecutions | queue_visible | queue_inflight | SQS最古滞留(s) | router IteratorAge(ms) |
|-----------|----------------------|---------------|----------------|----------------|------------------------|
| 17:22 | 122 | 1,198 | 2 | 2 | 2,541 |
| 17:23 | 243 | 5,978 | 122 | 60 | 1,363 |
| 17:24 | 364 | 8,432 | 208 | 89 | 1,539 |
| 17:25 | 471 | 9,518 | 345 | 93 | 1,590 |
| 17:26 | **502（ピーク）** | 6,288 | 460 | 74 | — |
| 17:27 | （終了） | 0 | 0 | — | — |

- **ピーク 502 多重**（Pipes 版は同条件で 1,000）。Errors 0、worker Throttle 0、unit Throttle 0。
- **送信 24,000 / 削除 24,000（取りこぼしなし）。** 入口が違っても個体は欠落しない。
- worker Duration avg ~3,084ms / p99 ~3,569ms（Pipes 版と同じ＝下流は同条件）。
- **中継 Lambda IteratorAge 最大 2,541ms**（Pipes 版は `AWS/Pipes` 未発行で観測不可）。

**解釈（T3 の答え）**

502 は「中継 Lambda の限界値」ではなく、**この投入量・この時間での到達値**である。重要なのは形:
`queue_visible` が 9,518 まで積み上がり（滞留は潤沢）、17:26 に 6,288 → 17:27 に 0 へ急落して worker も終了した。
つまり **worker が 502 まで立ち上がった時点で、中継 Lambda が 24,000 件を SQS に送り終え、残りを数十秒で
捌いて完了した**。Pipes 版（試行 2）は worker が 1000 まで立ち上がる前に供給が続いたのに対し、
中継 Lambda 版は worker の立ち上がり（1 分 60 増）が追いつく前に供給が尽きた。

差を生んだのは**入口の供給の速さ**: 中継 Lambda は unit テーブルの Streams を ESM で読む段が
**S×P の壁**（オープンシャード数 × 並列化係数。第 3 回で詰まった壁）に律速され、SQS への供給レートが
Pipes より低い。IteratorAge 2,541ms がその遅れ（Streams 読み出しが処理に遅れている）を示す。
**同じ下流でも「入口の速さ」が worker の到達多重に直結した**のが本検証の収穫。

> 中継 Lambda 版でも、もっと長く・厚く供給を続ければ 1000 に届く可能性はある（S×P の壁が SQS 供給
> レートにどう効くか次第）。502 は上限ではなく、Pipes と同条件での到達値である点に注意。

**業務から見た所要時間（roast-batch の `labeling_started_at` → `labeling_finished_at`）**

CloudWatch メトリクスとは別に、業務データ側のタイムスタンプから「付番開始 → 全個体 LABELED」の
実時間を両方式で比較した（どちらも 20 バッチ全て LABELED、取りこぼし 0）。

| | 方式 A-Pipes | 方式 A-Lambda（P=1） | 方式 A-Lambda（**P=10**） |
|---|-------------|---------------------|--------------------------|
| **1 バッチ（1,200 個体）の付番所要・中央値** | **9 秒** | **93 秒**（約 10 倍） | **9 秒**（Pipes と同じ） |
| 1 バッチ所要 min / max | 8 / 15 秒 | 63 / 104 秒 | 8 / 11 秒 |
| 全 20 バッチの総所要（最初の start → 最後の finish） | 226 秒 | 281 秒 | 227 秒（Pipes と同じ） |

**P=10 で業務時間まで Pipes と並ぶ。** 1 バッチ 9 秒・総所要 227 秒は Pipes（9 秒・226 秒）とほぼ完全一致
（差 1 秒）。CloudWatch のピーク多重（1000 vs 1000）だけでなく、**業務から見た実処理時間でも区別がつかない**。
中継 Lambda の「10 倍遅い（93 秒）」は方式の限界ではなく `ParallelizationFactor=1`（既定）のためで、
P=10（S×P=40）にすれば Pipes と同等になる。設定一つで 10 倍差が解消する。

- **1 バッチあたり 9 秒 vs 93 秒（約 10 倍差）が本質的な差。** 「1 回の焙煎バッチ完成をトリガーに
  その 1,200 個の付番が終わるまでの業務応答時間」であり、現場感覚に直結する。中継 Lambda は
  Streams 読み出しが S×P で律速され、1 バッチ分を SQS へ送り切るのに時間がかかるため完了が遅い。
- **全 20 バッチの総所要の差（226 vs 281 秒＝55 秒）は小さい。** これは 20 バッチを STAGGER 10 秒で
  順次投入（投入だけで ~190 秒）しており、投入時間が支配的なため。方式の差は「最後のバッチ投入後に
  捌け切るテール」に表れる。方式比較としては 1 バッチ所要（9 秒 vs 93 秒）を見るのが妥当。
- CloudWatch の「ピーク 1,000 vs 502」と、この業務データの「1 バッチ 9 秒 vs 93 秒」は同じ現象の両面
  （供給が遅い → worker が立ち上がりきらない → 1 バッチの捌け切りが遅い）。

## 4.6 試行 4〜6 — 中継 Lambda 版: 供給量を増やすと worker は伸びるか（S×P の壁の検証）

中継 Lambda 版（`RELAY_MODE=lambda`、`PROCESSING_TIME_MS=3000` 固定）で、**投入量だけ**を増やして
worker のピーク多重がどう変わるかを見た（1 変数のみ変更）。あわせて中継 Lambda（router）自身の
同時実行を観測し、S×P の壁を直接確認した。

**unit テーブル Streams: オープンシャード数 S=4 / router ESM ParallelizationFactor P=1 → S×P=4。**

| 試行 | 投入（個体） | worker ピーク | router 同時実行（実測） | 1000 到達まで | SQS最古滞留 |
|------|-------------|--------------|------------------------|--------------|------------|
| 4 | 20 バッチ（24,000） | 502 | 5〜6 | 未到達 | 93 秒 |
| 5 | 30 バッチ（36,000） | 800 | 5〜6 | 未到達 | 68 秒 |
| 6 | 50 バッチ（60,000） | **1,000** | **7** | **+360 秒** | 15 秒 |

いずれも取りこぼし 0（送信=削除）、worker Errors/Throttle 0、unit Throttle 0、Duration avg ~3,050〜3,160ms。

**発見（SQS を挟む意味そのもの）**

- **router 同時実行は投入量によらず常に S×P（4〜7）に張り付く**。中継 Lambda の Streams 読み出しは
  S×P の壁に律速され、SQS への**供給レート**は一定の天井を持つ（第 3 回の壁がそのまま入口に残る）。
- **一方で worker のピークは 502 → 800 → 1,000 と投入量に比例して伸びた。** SQS がバッファとして挟まる
  ことで、入口の S×P（供給レート）と worker の到達多重が**デカップリング**されている。
- 結論: **S×P は供給の「レート」を縛るが、worker の「到達多重」は供給の「総量 × 継続時間」で決まる。**
  細い供給（S×P=4）でも、長く供給し続ければ worker は 1,000 まで積み上がる。これが
  「Streams 直読みは S×P=640 で頭打ち（第 3 回）」に対し「SQS を挟めば 1,000 到達」の正体。

**Pipes 版との差（同じ 1000 到達でも「速さ」が違う）**

| | 方式 A-Pipes | 方式 A-Lambda |
|---|-------------|---------------|
| 1000 到達に要した投入 | 24,000（20 バッチ） | 60,000（50 バッチ）＝ **2.5 倍** |
| 1000 到達まで | +60〜120 秒 | +360 秒 |
| 供給レートの天井 | 速い（S×P 制約を受けにくい） | S×P=4 で細い（router 同時実行 5〜7） |

どちらも 1000 到達・取りこぼし 0 だが、中継 Lambda は S×P で供給が細いぶん「2.5 倍の量を 3 倍の時間
かけて」ようやく届く。Pipes は一気。方式の本質的な差は「到達可否」ではなく「入口の供給レート」。

## 4.7 試行 7 — 中継 Lambda の ParallelizationFactor P=10（S×P=40）で Pipes に並ぶか

試行 4（P=1・20 バッチ・502 止まり）と**投入を完全に同じ**（20 バッチ・24,000 個体・STAGGER 10s・
`PROCESSING_TIME_MS=3000`）にし、**ESM の `ParallelizationFactor` だけ 1 → 10** に変えた（S×P=4→40）。
投入量・下流・D は Pipes 版（試行 2）とも揃うので、同じ 20 バッチで Pipes / P=1 / P=10 の 3 者が並ぶ。

**同じ 20 バッチ（24,000 個体）での 3 者比較**

| 方式 | worker ピーク | 1000 到達まで | router 同時実行 | SQS最古滞留 | IteratorAge |
|------|--------------|--------------|----------------|------------|-------------|
| Pipes | 1,000 | +60〜120 秒 | 観測不可 | 3 秒 | 観測不可 |
| 中継 Lambda **P=1** | **502**（未到達） | 未到達 | 5〜7（S×P=4） | 93 秒 | 2,541ms |
| 中継 Lambda **P=10** | **1,000** | **+60 秒** | **40（S×P=40）** | **4 秒** | 1,575ms |

いずれも取りこぼし 0（送信=削除 24,000）、Errors/Throttle 0、Duration avg ~3,100ms。

**発見（T3 の最終的な答え）**

- **router 同時実行が S×P=40 ちょうどに跳ねた**（P=1 のとき 4〜7 → P=10 のとき 40）。
  ESM の `ParallelizationFactor` が供給並列度を線形に決めている直接証拠。これが「入口の供給レートの天井」。
- **P を 1→10 にするだけで、同じ 20 バッチで 502 → 1,000。** 到達 +60 秒・最古滞留 4 秒と、**Pipes とほぼ同等**。
- つまり **中継 Lambda 版の「遅さ」は方式の限界ではなく、`ParallelizationFactor` という設定で解消できる**。
  デフォルト（P=1）だと S×P=4 で Pipes に大きく劣るが、P=10（S×P=40）で Pipes に並ぶ。

**方式選択の結論（T3）**: 「Pipes vs 中継 Lambda」の単純な優劣ではない。
- **取りこぼし**: どちらも 0（at-least-once + 冪等が効く）。
- **速さ**: デフォルト設定では Pipes が速い。中継 Lambda も `ParallelizationFactor` を上げれば並ぶ。
- **トレードオフ**: Pipes はマネージドで速い・設定最小だが入口が CloudWatch で観測しにくい（`AWS/Pipes` 未発行）。
  中継 Lambda は自前実装で IteratorAge / 同時実行を観測でき、P で供給レートを調整できる自由がある代わりに
  S×P を意識した設計が要る。

## 4.8 試行 8 — 最速投入（seeder 並列化）と、オンデマンドの書き込み（T2・学習）

投入方法の差を見るため、**投入速度だけ**を最大化した（他は P=10 の試行 7 と同じ: lambda・P=10・D=3000・20 バッチ）。
変更点は 2 つとも「投入を速くする」方向: `SEED_WRITE_CONCURRENCY=48`（seeder の BatchWriteItem を
48 並列）＋ `STAGGER_SEC=0`（20 seeder を一斉起動）。

| 指標 | 試行 7（STAGGER=15・seeder 直列） | 試行 8（STAGGER=0・seeder 48 並列） |
|------|-----------------------------------|-------------------------------------|
| worker ピーク | 1,000 | **948**（むしろ低い） |
| 1000 到達 | +60 秒 | 未到達 |
| SQS 最古滞留（最大） | 4 秒 | **78 秒** |
| seeder Duration avg / max | （直列・数秒） | **~507ms / ~1,595ms**（並列化で短縮） |
| unit WCU（1 分 Sum ピーク） | ~13,000 | **~25,236**（約 2 倍のレート） |
| **unit WriteThrottleEvents（T2）** | **0** | **0** |

**発見 1: 最速投入は worker 到達をむしろ下げた（投入方法の差）。**
seeder 48 並列で 24,000 件を 1〜1.5 秒で Streams に叩き込めた（WCU レートは約 2 倍）。だが worker は
948 止まり・滞留 78 秒・IteratorAge 1,859ms。原因は入口: 中継 Lambda は S×P=40 でしか Streams を
読めない（router 同時実行 41）ため、瞬間的に積んだ 24,000 件を吸い出すのが追いつかず、SQS への供給が
むしろムラになった。**投入を速くしても入口（S×P）が一定なら worker の立ち上がりは改善せず、むしろ悪化しうる。**
worker をきれいに立ち上げるには「速く叩き込む」より「入口が一定レートで供給し続ける」ほうが効く。

**発見 2: オンデマンドは本検証のレート（瞬間 ~420 WCU/秒、GSI 2 本込みで実質その数倍）を
スロットルなしで吸った（T2 は再び 0）。** ただしこれは**学習済みのテーブル**での結果である点に注意:
本日すでに 1000 多重の書き込みを何度も通しており、オンデマンドが観測ピークに追従してパーティションを
分割済みと考えられる。**「初動スロットル」を観測するにはテーブルをリセット（再作成）して学習前の 1 発目を
測る必要がある**（本検証では未実施）。T2 を一度も観測できなかったことは「このレートは吸える」と
「既に学習済み」の両方を含み、本検証のデータだけでは分離できない。

**過去の結論への影響（重要）**: 本検証では **WriteThrottleEvents が全試行で 0**＝書き込みは一度も
ボトルネックにならなかった。したがって §4.2〜§4.7 の結論（1000 到達・方式比較・P の効果・業務時間）は
**テーブルの書き込み学習状態に依存しない**。worker の到達多重を律速したのは一貫して「SQS→Lambda の
スケール」「入口の供給レート（S×P）」「投入総量」であり、DynamoDB の書き込み側ではない。

**発見 3: Lambda 同時実行枠の食い合いは、この回では起きていなかった（が一般には要注意）。**
アカウント・リージョンの Lambda 同時実行枠は全関数で共有（本アカウントは 1000）。worker + 中継 Lambda
（router）+ seeder が枠を食い合って worker が 1000 に届かない可能性を疑い、948 の回で 3 関数の同時実行を
同時刻で突き合わせた:

| 時刻(JST) | worker | router | seeder | 合計 |
|-----------|--------|--------|--------|------|
| 11:32 | 455 | 41 | 2 | 498 |
| 11:33 | 760 | 40 | 1 | 801 |
| 11:34 | **948** | **0** | **0** | **948** |

worker が 948 のピークに達した 11:34 には router も seeder も既に 0（中継・投入とも完了）。合計 948 で
枠 1000 に 52 の余裕があり、**この回の 948 止まりは枠の食い合いではなく供給切れ**（router が 40→0 に
落ち、SQS への供給が止まった）。前述の「最速投入は S×P で供給がムラになり逆効果」の裏付けでもある。

ただし**構造的には食い合いは起こり得る**: router（P=10 で ~40 並列）＋ seeder（並列投入中）＋ worker
（立ち上がり中）が**同時にピークを迎える**条件なら、合計が 1000 に当たって worker が頭打ちになる。
**Pipes 版が枠の心配なく 1000 に張り付けたのは、Pipes が Lambda 同時実行枠を使わない（マネージド）**
という隠れた優位でもある。中継 Lambda 版は router が枠を食うぶん worker の取り分が目減りする点は、
第 2 本（並行数制御・下流保護）の論点として残す。

## 4.9 試行 9 — STAGGER=0・30 バッチで 1000 到達、そして初の worker Throttle（食い合いの実証）

最速投入（seeder 48 並列・STAGGER 0）のまま**総量を 36,000（30 バッチ）に増やして**供給時間を量で
カバーした。入口は中継 Lambda（P=10）。結果 **worker ピーク 1,000 到達**（+60 秒）。取りこぼし 0、
router 同時実行 40（S×P）、unit WriteThrottle 0。

**初めて worker Throttle（2 回）を観測。** 枠の食い合いの瞬間が捉えられた:

| 時刻(JST) | worker | router | seeder | 合計 | worker Throttle |
|-----------|--------|--------|--------|------|----------------|
| 11:46 | 879 | 40 | 2 | 921 | 0 |
| 11:47 | **1,000** | 0 | 0 | **1,000** | **2** |
| 11:48 | 1,000 | 0 | 0 | 1,000 | 0 |

- worker が 1,000 に張り付いた 11:47 に Throttle が 2 発生。11:46 時点では worker 879 + router 40 +
  seeder 2 = 921 で枠内。
- **Throttle の原因は（当初疑った「食い合い」ではなく）worker 自身が `MaximumConcurrency`=1000 の
  天井に当たったこと**。この点は §4.10 の Pipes 版（router なし・seeder 0 でも worker 1000 到達時に
  Throttle=1）との対照で確定した。worker の `MaxConc`（1000）とアカウント枠（1000）が同値なので、
  SQS イベントソースがさらにスケールしようとすると天井に当たり軽微に Throttle する。
- **ただし「食い合い」の構造的リスクは別途正しい**: 11:46 のように worker 879 + router 40 が併存する
  状況で、もし worker が router と同時に 1000 近くまで立ち上がれば合計が枠に当たり worker は ~960 で
  頭打ちになり得た。今回は worker が 1000 に乗る頃には router が 0 に落ちていたため顕在化しなかった。
  対策は worker の MaxConc を枠より小さく取る／アカウント枠を引き上げる／入口を Pipes にして枠を
  使わない、のいずれか（第 2 本の論点）。

## 4.10 試行 10 — 同条件で Pipes（STAGGER=0・30 バッチ・seeder 48）: 最速投入の正面比較

試行 9（中継 Lambda P=10）と**入口以外すべて同じ**（Pipes・seeder 48 並列・STAGGER 0・30 バッチ・
D=3000）で Pipes 版を流し、最速投入どうしで正面比較した。

| | 中継 Lambda P=10（試行 9） | Pipes（試行 10） |
|---|----------------------------|------------------|
| worker ピーク | 1,000 | 1,000 |
| 1000 到達まで | +60 秒 | +60 秒 |
| worker Throttle | 2 | 1 |
| router 同時実行 | 40（S×P） | なし（Lambda 枠を使わない） |
| SQS 最古滞留（最大） | 80 秒 | 58 秒 |
| 取りこぼし（送信=削除） | なし（36,000） | なし（36,000） |

**発見**

- **この条件（総量 36,000 の最速投入）では両方式とも 1000 到達・+60 秒でほぼ互角。** 試行 2/7 で
  Pipes が優位だったのは「供給レートの差（S×P）が worker 立ち上がりに効いた」からで、総量を増やして
  供給時間を確保すれば中継 Lambda も Pipes に並ぶ。
- **worker Throttle は両方式とも worker が 1000 に達した瞬間に発生**（Lambda 2 / Pipes 1）。Pipes 版は
  router が居らず seeder も 0 のときに Throttle=1 が出たことから、**Throttle の原因は入口方式ではなく
  worker 自身の MaxConc=1000 の天井**だと確定（§4.9 の当初解釈を訂正）。
- 差が残るのは **SQS 最古滞留（Pipes 58 秒 < Lambda 80 秒）** と router が Lambda 枠を使うか否か。
  Pipes は供給が速く枠も使わないぶん、同じ 1000 でもキューの新鮮さと枠の余裕で優る。

**業務時間（付番開始 → 全個体 LABELED）でもほぼ互角（わずかに Pipes 優位）**

| | 中継 Lambda P=10（試行 9） | Pipes（試行 10） |
|---|----------------------------|------------------|
| 全 30 バッチの総所要（最初 start → 最後 finish） | 135 秒 | **129 秒** |
| 1 バッチ所要・中央値 | 63 秒 | **56 秒** |
| 1 バッチ min / max | 15 / 95 秒 | 13 / 90 秒 |

全体 6 秒差・1 バッチ中央値 7 秒差で、実用上は誤差レベル。CloudWatch のピーク多重・立ち上がりに続き
業務時間でもほぼ並ぶ。

**重要な業務トレードオフ（投入方法の差）**: 同じ 1000 到達でも、1 バッチ中央値は STAGGER=10・20 バッチ
（試行 2/7）では **9 秒**だったのが、STAGGER=0・30 バッチ（試行 9/10）では **56〜63 秒**に伸びた。
最速投入（STAGGER=0）で 36,000 個体を短時間に積むと SQS 滞留が 58〜80 秒に膨らみ、各バッチの個体が
キューで長く待つため 1 バッチの完了が遅くなる。一方で全体の総所要は短い（135/129 秒で 36,000 件完了）。
**「全体スループットを上げる（一気に投入）」と「1 バッチの応答を速くする（分散投入）」は別物**で、
「焙煎 1 バッチ完成ごとに早く付番結果が欲しい」業務なら投入を分散させるほうが体感が良い。

> CloudWatch Logs Insights で worker の START/END ログから再構成する（本検証では未実施＝案 C）。
